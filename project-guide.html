PROJECT GUIDE

기술보다 문제에서 시작하세요

졸업작품은 새로운 기술을 보여주기 위한 결과물이 아니라, 실제 사용자가 겪는 기존 문제를 발견하고 소프트웨어 서비스로 해결하는 과정입니다.

주제 선정 시작하기 ↓선배 작품 살펴보기 ↗
01

“무엇을 만들까?”보다 “어떤 문제를 해결할까?”

기능이나 기술을 먼저 정하면 사용 이유가 약한 결과물이 되기 쉽습니다. 주변의 불편을 관찰하고, 누가 언제 어떤 어려움을 겪는지 확인한 뒤 해결 방법을 설계하세요.

문제 발견부터 포트폴리오까지

거창한 아이디어보다 분명한 사용자와 검증 가능한 문제에서 시작합니다.

01문제 발견

반복되는 불편을 관찰하고 현재 해결 방식의 한계를 기록합니다. 사용자에게 실제로 중요한 문제인지 근거를 모으세요.

  • 관찰 기록 · 기존 서비스 비교
02사용자 정의

모든 사람이 아니라 누가 언제 어디서 문제를 겪는지 정하고 실제 사용자를 만나 확인합니다.

  • 사용자 인터뷰 · 핵심 문제 한 문장
03데이터/API 조사

필요한 데이터의 출처·품질·이용 조건과 API 제한을 확인합니다. 개인정보 수집을 최소화하세요.

  • 출처 · 라이선스 · 호출 제한 · 대체 방안
04기능 정의

사용자의 시작부터 완료까지 흐름을 그리고 해결에 꼭 필요한 기능을 우선순위로 정합니다.

  • 사용자 시나리오 · 완료 조건
05기술 스택 선택

AI·LLM·클라우드를 먼저 정하지 말고 문제와 제약에 맞는 가장 단순한 기술을 선택합니다.

  • 선택 이유 · 팀 역량 · 운영 비용
06MVP 범위 설정

핵심 기능 1~3개로 처음부터 끝까지 동작하는 작은 서비스를 만듭니다. 이번에 하지 않을 일도 명시합니다.

  • 핵심 흐름 · 범위 제외 · 일정
07GitHub Repository 관리

Issue로 작업을 나누고 의미 있는 커밋과 코드 리뷰를 남깁니다. 비밀 값과 개인정보는 저장소에 넣지 않습니다.

  • Issue · 브랜치 · Pull Request · .gitignore
08README 작성

문제·사용자·핵심 기능·구성도·실행 방법과 팀의 기여를 기록합니다. 다른 사람이 재현할 수 있게 작성하세요.

  • 설치 · 환경 변수 예시 · 사용 화면
09테스트

기능의 정상·오류 경로와 모바일·키보드 접근성을 확인합니다. 실제 사용자의 피드백으로 문제가 줄었는지 검증합니다.

  • 테스트 기록 · 오류 재현 · 전후 변화
10배포 또는 시연

접속 가능한 환경이나 재현 가능한 시연을 준비하고 설정·권한·복구 절차를 확인합니다.

  • 데모 주소 · 시연 영상 · 운영 제한
11포트폴리오 정리

문제와 해결 근거, 맡은 역할, 기술 선택의 이유와 개선점을 설명합니다. 결과뿐 아니라 판단 과정도 보여주세요.

  • GitHub · 화면 · 테스트 결과 · 회고

주제 정의 한 문장

[사용자]가 [상황]에서 겪는 [문제]를 해결하기 위해, [핵심 기능]을 제공하는 서비스를 구현한다.

예시 — 프로젝트실을 이용하는 학생이 빈 공간과 예약 현황을 알기 어려운 문제를 해결하기 위해, 실시간 예약 및 사용 현황 서비스를 구현한다.

좋은 주제인지 점검하기

  • 실제 사용자를 만날 수 있는가?
  • 문제를 관찰하거나 근거로 설명할 수 있는가?
  • 한 학기 안에 핵심 흐름을 구현할 수 있는가?
  • 사용 전후의 변화를 확인할 수 있는가?

기술 선택 원칙

  • AI·빅데이터가 꼭 필요한 이유가 있는가?
  • 기술 없이 더 단순하게 해결할 수는 없는가?
  • 개인정보와 편향 문제를 고려했는가?
  • 기술 설명보다 사용자 가치를 먼저 말할 수 있는가?

선배들의 결과물에서 문제 해결 방식을 찾아보세요

작품을 그대로 따라 하기보다 어떤 문제를 어떻게 정의하고 구현했는지 살펴보세요.
